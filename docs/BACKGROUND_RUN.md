# Долгий запуск на Windows

`pipeline.py run JOB` остаётся синхронным. Для работы после закрытия консоли:

```powershell
.\venv\Scripts\python.exe scripts\pipeline.py start NEW_JOB
.\venv\Scripts\python.exe scripts\pipeline.py background-status NEW_JOB
.\venv\Scripts\python.exe scripts\pipeline.py status NEW_JOB
```

`start` возвращает квитанцию отправки. Успех отправки ещё не означает готовый PDF:
дождаться `background-status: done` и обычного `status: done`.
Во время регистрации задачи статус может быть `starting`: до квитанции запуска
предусмотрено окно 30 секунд. Ошибки отправки/загрузки worker и запрос отмены
не маскируются этим ожиданием; зависшая отправка переходит в `needs_attention`.
Существующий корректный готовый результат повторно не запускается.
Изменившиеся настройки, код или повреждённый результат требуют разбора причины.

Однократная задача Windows Task Scheduler запускает `pythonw.exe` из окружения
проекта. Principal — SID текущего вошедшего пользователя, InteractiveToken,
обычные права. Пароль, SYSTEM, повышение прав, триггеры и автоматические повторы
не используются. Лимит времени задачи отключён; лимиты стадий конвейера сохраняются.
`pipeline.py` получает собственную скрытую консоль, не консоль отправителя.
Поэтому проверяется фактический запуск через службу Планировщика, а не название
команды `schtasks`, WMI или `start /b`.

Это устойчивость к Ctrl+C, закрытию окна отправителя и уничтожению его дерева
процессов через Job Object. Выход из учётной записи, перезагрузка и выключение
машины не покрываются. После прерывания нужен явный запуск и проверка статуса;
кэш и успешные стадии сохраняются по существующим правилам.

## LM Studio

По умолчанию используется локальный endpoint из настроек задания; его внешний
процесс остаётся под управлением пользователя. Для собственного сервера:

```powershell
.\venv\Scripts\python.exe scripts\pipeline.py start NEW_JOB --start-lmstudio `
  --lmstudio-models "D:\Models\lmstudio"
```

Задание заранее создать с `host`, указывающим на свободный loopback-порт.
Каталог моделей должен уже существовать и содержать установленные веса; запуск
не скачивает модели. По умолчанию новый профиль создаётся в
`JOB/background/lmstudio-profile`. Другой путь: `--lmstudio-profile PATH`.
Установленный движок инференса можно явно передать через
`--lmstudio-backend PATH`: путь к каталогу одного backend с
`backend-manifest.json`. Этот движок и перечисленные в его манифесте соседние
vendor-библиотеки копируются в новый профиль; исходные файлы только читаются.
Снимок проверяется по отдельному инвентарю. Это нужно, когда установщик LM Studio
уже перенёс встроенные движки в обычный профиль: одних GGUF-весов недостаточно.
Не передавайте весь каталог моделей или каталог нескольких версий вместо одного
движка. Автоматического поиска, установки или обновления движков этот параметр
не выполняет.
Профиль внутри исходного движка/vendor запрещён до копирования; проверяются
точный состав копии, хэши и отсутствие ссылок, ведущих за её границы.
При необходимости явно задать `--lms-exe PATH` и `--lmstudio-app PATH`.
Последний принимает установленный `LM Studio.exe` или официальный `llmster.exe`.
Таймаут готовности `--startup-timeout` по умолчанию 120 секунд.

Старые пользовательские профили не принимаются за собственные. Сервер должен
подтвердить текущего пользователя, PID/время создания, исполняемый файл,
аргумент отдельного профиля и принадлежность слушающего порта. Перед GPU-OCR
выгрузка идёт через API именно этого сервера; при ошибке принадлежности нет
перехода к глобальному `lms unload --all`. После завершения останавливается
только собственный сервер. Посторонний сервер не останавливается ради запуска.

Установленная версия LM Studio может запрещать несколько одновременных ядер
даже при разных профилях. Отдельный профиль сам по себе этого не гарантирует.
Запуск заранее отказывает при работающем другом ядре; автоматической остановки
чужого экземпляра нет. Для перехода с уже работающего сервера сначала завершить
его обычным способом. Ограничение и результаты теста фиксируются в INTEGRITY.md.

## Статус, логи и отмена

Квитанции: `JOB/background/latest.json` и `run-UUID/`. Внутри находятся
неизменяемый запрос, `state.json`, UTF-8 `worker.log`, `pipeline.log`, данные
регистрации задачи и отметки её удаления. Запрос привязан к хэшам задания и кода;
смена кода после отправки останавливает запуск до стадий.

```powershell
.\venv\Scripts\python.exe scripts\pipeline.py stop NEW_JOB
```

Отмена адресуется конкретному запуску и его процессам. При потерянном supervisor
используются записанные PID вместе со временем создания. Подмена PID не даёт
права остановить новый процесс. Неустановленная принадлежность требует разбора.
`needs_attention` и `failed` не перезапускаются автоматически. Ошибка связи с
Планировщиком также не запускает запасной экземпляр: задача могла уже стартовать.
Статус `done` появляется после проверки PDF и успешной очистки собственного
сервера/задачи; ошибку очистки нельзя выдавать за успех.

## Изолированная проверка

```powershell
.\venv\Scripts\python.exe tests\run_detached_integration.py --out NEW_TEST_DIR
```

Тест создаёт свои консоли, обычный контрольный дочерний процесс, mock MT-сервер
и синтетический вход. Прерывание вводится во время настоящего запроса перевода.
Контроль должен погибнуть, фоновые процессы — ответить на новый запрос и выпустить
PDF через настоящий Pandoc/XeLaTeX. Тесты не используют готовую книгу как фикстуру.
Реальный LM Studio проверяется отдельным opt-in тестом; он не входит в smoke.

Приёмка 25.10.2026: все три сценария конвейера прошли. Отдельный реальный
`llmster 0.0.25-1` пережил закрытие консоли; после события продолжались heartbeat
и HTTP-запросы. Native API подтвердил отсутствие загруженных моделей. По явному
разрешению пользователя обычный пустой сервер временно остановили и восстановили
на прежнем порту; хэши трёх исходных файлов настроек совпали. Проверка не измеряет
качество перевода или скорость инференса. Runtime для испытания скачан с официального
источника в отдельный каталог, проверен по SHA-512 и не входит в пакет конвейера.
Его архив содержит встроенную embedding-модель; в память она не загружалась.

Дополнительно выполнен полный маленький цикл на **настоящей Hy-MT2-7B Q8_0**:
новый синтетический Markdown, собственный профиль, явно выбранный установленный
CUDA backend 2.29.1, закрытие консоли отправителя во время работы → перевод →
Pandoc/XeLaTeX → принятый PDF из трёх страниц. Native API наблюдал контекст 8192
до/после запросов; настройки контекста не подменялись. Все три математические
маски восстановлены, ошибок/предупреждений финального TeX-лога нет.
Повторный `start` вернул `done` без нового запуска. Собственный сервер/порт/задача
освобождены, обычный сервер 1234 восстановлен пустым; четыре исходных файла
настроек и инвентарь движка совпали по SHA-256, размер/mtime весов не изменились.
Это проверка запуска и маленького Markdown→PDF, без OCR и без полной книги.
