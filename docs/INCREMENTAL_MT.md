# Возобновляемый перевод без повторения принятых фрагментов

Изменение 2026-11-15; включено в публичный выпуск beta.5 от 16.11.2026.
Маршрут книги остаётся `scripts/pipeline.py init → plan → run → status`.
Локальная модель, настройки задания и запрет автоматической полировки/облака не меняются.

## Причины лишней работы

1. Успех сохранялся только после перевода всей группы: сбой последнего запроса
   терял уже принятые результаты предыдущих запросов.
2. Ошибка одного абзаца приводила к повтору всей группы. Длинные маркеры
   абзацев, полный глоссарий и плохо разделённые блоки увеличивали запросы.
3. Внешний контроллер повторял одинаковую ошибку без ограничения числа запусков,
   в том числе при отключённом сервере и отсутствии работы для targeted repair.
4. Изменение любого кода оркестратора делало старое извлечение «устаревшим».
   Сборка каждый раз начиналась в новой папке; Missing character выявлялся поздно.
5. Некоторые быстрые пути проверяли хеши, но пропускали текущий валидатор.
   Прежнее изменение греческих пунктов также ослабило проверку пропусков внутри строки.

## Алгоритм

- Прежние групповые ключи и файлы читаются без миграции. Новые варианты старой
  записи добавляются в `revisions-v1`, не заменяют историческую запись.
- Каждый принятый запрос немедленно сохраняется отдельно в `fragments-v1`.
  После прерывания возобновление использует эти контрольные точки.
- Если ответ группы имеет точные ID, порядок и границы абзацев, каждый абзац
  проверяется отдельно. Исправные сохраняются; только отвергнутые отправляются
  по одному, без длинной оболочки ID. При неоднозначных границах ответ не разбирается.
- Неудачная стратегия группы запоминается отдельно от переводов. Следующий запуск
  сразу переходит к небольшим запросам. Эта отметка не означает принятия ответа.
- Одинаковые запросы в параллельных потоках имеют одного производителя.
- Любое повторное использование проверяет текущие числа, формулы, таблицы,
  маски, маркеры сносок, буквенные пункты, утечки инструкций и политику длины.
  Быстрый путь по предыдущему отчёту дополнительно проверяет покрытие абзацев.
- Переполнение контекста и постоянные HTTP 4xx останавливают запрос без бесполезных
  повторов. Временные ошибки имеют ограниченное число попыток.
- `pipeline_queue.py JOB...` последовательно вызывает штатный `pipeline.py run`.
  Максимум три запуска на задание для временных сетевых ошибок; при недоступном
  сервере перед повтором выполняется проверка доступности. Ошибки валидации,
  конфигурации и вёрстки автоматически не повторяются. Пользовательские внешние
  контроллеры не входят в пакет и не должны бесконечно перезапускать задание.
- Извлечение имеет собственный ключ исходника, режима, размера частей и кода
  извлечения. Старые квитанции принимаются только с доказуемым прежним ключом;
  неизвестное происхождение не «исправляется» переписыванием хеша.
- Подготовленный LaTeX привязан к переводу, параметрам, коду вёрстки, assets и
  рисункам. Прерванная сборка использует свои контрольные точки. Готовая сборка
  повторно сверяет зависимости, PDF и лог. Неизменившаяся детерминированная ошибка
  требует исправления входов, а Missing character останавливает первый затронутый проход.
- Текст, ошибочно попавший внутрь display-math, обрабатывается до основного MT.
  Сохранённые результаты этой стадии проверяются по настройкам и текущим правилам.

## Проверка

### Регрессии с mock HTTP

Регрессии находятся в `tests/test_incremental_mt.py` и `tests/test_stage_checkpoints.py`.
Они считают запросы к имитатору модели, проверяют прерывание, смену политики,
повреждение кэша/сборки, отрицательные примеры и ограниченность контроллера.
Все тесты выполняются на синтетических материалах; готовая книга не служит fixture.

```powershell
.\venv\Scripts\python.exe -X utf8 -m pytest tests -q
.\venv\Scripts\python.exe -X utf8 tests\run_smoke.py
.\venv\Scripts\python.exe -X utf8 tests\run_integrations.py --out <новый-каталог-на-E>
```

Число обращений проверяется точно. Ускорение реальной модели зависит от доли
ошибочных блоков и скорости генерации; измерение на mock API не является
измерением времени перевода книги. Техническая приёмка не заменяет смысловую редактуру.

### Проверка на настоящей Hy-MT2 (15.11.2026)

На `hy-mt2-7b` Q8_0 с контекстом 16 384, `parallel=1`,
`group_chars=900` и `split_chars=900` проверен новый синтетический EN→RU фрагмент.
Первый перевод и PDF: 3 запроса, 60,464 с. Повтор того же задания: 0 запросов,
0,219 с, без изменений файлов и новых проходов TeX.

В отдельную копию кэша перенесены только четыре принятые записи абзацев
(заголовок и три абзаца), без последнего абзаца, групповых кэшей и готового
выхода. Модель получила только недостающий абзац: 1 запрос, 7,341 с.
Четыре готовых фрагмента сохранились побайтно; повтор MT — 0 запросов, 0,381 с.
Счётчик `fragment_cache.reused=8` учитывает повторные чтения четырёх записей.

PDF принят: 3 страницы, 1 закладка, три формулы восстановлены точно,
`Missing character=0`, `kept_source=0`. В этом живом прогоне не вызывались
ошибочный ответ модели или аварийное прерывание; отрицательные сценарии
проверены отдельными регрессиями. Условия, метод и ограничения измерения:
[LIVE_HYMT_CACHE_CHECK.md](LIVE_HYMT_CACHE_CHECK.md).

### Прерывание внутри незавершённой группы

Отдельный живой тест выполнен 15.11.2026, результаты внесены 16.11.2026.
При `group_chars=900`, `split_chars=280` два абзаца успели пройти приёмку
до остановки процесса во время третьего запроса. Кэша всей группы и готового
отчёта ещё не было. После подтверждения `interrupted` обычный `run` отправил
модели только абзацы 3 и 4; переводы первых двух и четыре старые записи кэша
сохранились побайтно. `fragment_cache.reused=2`.

Возобновление с PDF: 2 новых запроса, 42,255 с. Повтор готового задания:
0 запросов, 0,181 с. Повтор третьего, ещё не принятого запроса ожидаем;
принятые абзацы повторно не переводились. Проверено завершение клиентского
процесса через `pipeline.py stop`; отключение питания и повреждение диска
не моделировались. Подробности: [LIVE_HYMT_INTERRUPT_CHECK.md](LIVE_HYMT_INTERRUPT_CHECK.md).
